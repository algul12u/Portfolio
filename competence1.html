Auto-positionnement

Au cours de ma troisième année de BUT Informatique, j’ai développé ma capacité à adapter des applications à différents contextes techniques et supports. Je suis aujourd’hui capable de choisir une architecture adaptée aux besoins d’un projet, d’intégrer plusieurs technologies cohérentes entre elles et de faire évoluer une application existante tout en conservant sa maintenabilité. Je considère néanmoins pouvoir encore progresser sur certains aspects liés au déploiement avancé et à l’industrialisation complète des environnements de production.

Situation 1

SAE 5 : Développement avancé — Jardins de Cocagne

Dans le cadre de la SAE5, mon groupe et moi avons développé une application destinée aux Jardins de Cocagne afin de gérer les adhérents, les paniers, les dépôts, les tournées et les livraisons. L’objectif était de proposer une solution web robuste, évolutive et adaptée à des besoins métiers relativement complexes.

Pour répondre à ces contraintes, nous avons choisi une architecture reposant sur :

  • Symfony pour le backend ;
  • Twig pour le rendu des interfaces ;
  • Bootstrap pour le responsive design ;
  • MySQL pour la persistance des données ;
  • Docker / Docker Compose pour la conteneurisation ;
  • GitLab pour le versionning et l’environnement collaboratif.

Ce projet m’a permis de comprendre qu’une application ne doit pas uniquement fonctionner techniquement : son architecture doit aussi faciliter la maintenance, les évolutions futures et le travail collaboratif.

J’ai participé à la réflexion sur les choix technologiques et sur la structuration générale du projet. Le recours à Symfony et au modèle MVC permettait une séparation claire entre logique métier, accès aux données et interface utilisateur. Cette organisation facilitait la compréhension du code et sa réutilisation future.

L’utilisation de Docker représentait également un apprentissage important. La conteneurisation permettait de reproduire le même environnement de développement sur plusieurs machines et de limiter les problèmes liés aux différences de configuration entre développeurs. Nous avons aussi intégré une logique de CI/CD via GitLab afin de préparer un environnement proche de la production.

Cette SAE m’a donc permis de développer l’AC « Choisir et implémenter les architectures adaptées » ainsi que « Intégrer des solutions dans un environnement de production ».

Situation 2

SAE 6 : Évolution mobile de l’application

La SAE6 consistait à faire évoluer l’application développée en SAE5 vers une version adaptée au mobile.

L’objectif n’était plus simplement de maintenir une application web existante mais de l’adapter à de nouveaux usages utilisateurs.

Deux profils distincts étaient pris en compte :

Partie client

  • consultation des tournées ;
  • suivi du livreur ;
  • visualisation des livraisons ;
  • QRCode panier ;
  • informations et statut de livraison.

Partie livreur

  • gestion de tournée ;
  • ordre des dépôts ;
  • scan QRCode ;
  • validation des livraisons ;
  • suivi d’avancement.

Cette SAE m’a particulièrement permis de comprendre la notion d’adaptation multi-support.

Il ne s’agissait pas uniquement de « recopier » l’application web sur téléphone, mais de repenser certaines fonctionnalités pour répondre aux contraintes mobiles :

  • ergonomie tactile ;
  • affichage simplifié ;
  • rapidité d’accès aux données ;
  • interactions terrain du livreur ;
  • utilisation du QRCode et du suivi de tournée.

Cette expérience m’a fait progresser sur l’AC « Faire évoluer une application existante ». J’ai compris qu’une évolution applicative implique souvent une remise en question de l’architecture initiale et une adaptation des fonctionnalités selon le contexte d’utilisation.

Situation 3

Stage 2026 — DSI Itelcom — Projet FDT

Durant mon stage chez Itelcom, j’ai développé un projet de dématérialisation de fiches de tâches (FDT) visant à remplacer un fonctionnement papier par une application web complète.

J’ai entièrement développé ce projet :

  • frontend HTML / CSS / JavaScript ;
  • backend PHP ;
  • stockage SleekDB ;
  • formulaires dynamiques ;
  • historique ;
  • archivage ;
  • collaboration utilisateur ;
  • sauvegarde automatique.

L’un des enjeux principaux concernait la flexibilité du système.

L’application devait pouvoir gérer plusieurs types de formulaires sans nécessiter une réécriture complète du code. Cette contrainte m’a amené à réfléchir davantage à l’organisation de l’application et à la structuration des données afin de rendre l’outil maintenable et évolutif.

J’ai également découvert l’importance d’adapter une application non seulement à des contraintes techniques mais également à son public utilisateur. Les utilisateurs n’étaient pas nécessairement issus du domaine informatique. L’ergonomie et la simplicité d’utilisation constituaient donc des critères essentiels.

Cette expérience a renforcé ma capacité à concevoir des applications adaptées à un contexte métier réel.

Bilan complémentaire

Ressources mobilisées et recul

Évolution constatée

Au début, je savais surtout développer des fonctionnalités isolées. Avec la SAE5, j’ai appris à raisonner en architecture complète : backend Symfony, base de données, interfaces Twig et environnement Docker. La SAE6 m’a ensuite obligé à penser l’évolution mobile, et le stage FDT m’a confronté à une adaptation métier réelle avec des formulaires dynamiques.

Ressources mobilisées en formation

J’ai mobilisé les enseignements de développement web, de bases de données, de conception MVC, d’IHM, de gestion de projet, de versionning Git et de qualité logicielle. Ces ressources m’ont aidé à structurer les données, organiser le code et justifier les choix techniques.

Ressources cherchées en autonomie

En complément, j’ai utilisé la documentation de Symfony, Twig, Bootstrap, Docker Compose, GitLab CI/CD, PHP, JavaScript et SleekDB. Durant le stage, j’ai aussi dû m’appuyer sur les règles métier internes et les retours des utilisateurs.

Meilleure maîtrise acquise

Ces expériences m’ont permis de mieux comprendre l’intérêt des notions vues en cours. Le MVC n’était plus seulement un principe théorique : il devenait une façon concrète de rendre une application maintenable. Docker, GitLab et les maquettes mobiles ont aussi pris du sens dans un contexte projet réel.

Si c’était à refaire

Je préparerais plus tôt une documentation technique de l’architecture, un plan de tests et une réflexion mobile dès la conception initiale. Cela permettrait de faciliter l’évolution vers de nouveaux supports et de mieux anticiper le déploiement.

Analyse réflexive

Recul personnel

Ces différentes expériences m’ont permis de comprendre qu’adapter une application ne consiste pas uniquement à coder des fonctionnalités.

Il faut être capable :

  • d’analyser le besoin réel ;
  • de choisir les technologies adaptées ;
  • de concevoir une architecture maintenable ;
  • de prendre en compte l’environnement technique ;
  • d’adapter l’application à ses utilisateurs et à ses supports.

La SAE5 m’a davantage apporté une compréhension architecturale et environnementale. La SAE6 m’a appris l’évolution multi-support. Le stage m’a confronté à une adaptation métier réelle avec des contraintes utilisateurs fortes.

Aujourd’hui, je me sens plus à l’aise pour concevoir ou faire évoluer une application web ou mobile en tenant compte des enjeux de maintenabilité, d’ergonomie et d’intégration technique.
